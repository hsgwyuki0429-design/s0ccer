# ネットコード設計

操作精度が最優先の要件なので、ネットワーク層は「入力遅延を体感させない」ことに全振りする。

## 1. 方式の選択

**サーバー権威 + クライアント予測 + リコンシリエーション**を採用する。

### なぜサーバー権威か

チート対策よりも先に、**全員の画面で同じことが起きることを保証するため**。
P2P やクライアント権威だと、ボールの位置が各クライアントでズレて「入った／入ってない」が食い違う。サッカーで得点の判定が食い違うのは致命的。

### なぜロールバック（GGPO 方式）ではないか

格闘ゲームで使われるロールバックは、2人・入力が離散的・巻き戻し量が小さい、という条件で強い。

本作は 6人・入力が連続値・ボールという共有オブジェクトがある。この条件だと他プレイヤーの入力予測を外した際の巻き戻しが頻繁かつ大きく、**ボールが飛ぶ方向が事後的に変わる**という最悪の見え方をする。よって不採用。

## 2. 何を予測するか — ボールを含む世界全体

**ボールも含めて全エンティティを予測する。**

当初は「自分の選手だけ予測し、他プレイヤーとボールは 100ms 遅延させて補間表示する」という、FPS で一般的な構成を想定していた。ボールを予測すると、キックの瞬間に飛ぶ方向が事後修正されうるためだ。

**しかしサッカーではこれが成立しない。** ボールを補間表示にすると、キックボタンを離してからボールが動いて見えるまで **RTT + 補間遅延 ≈ 130ms** かかる。「同じ操作なら同じ球が飛ぶ」を物理側でいくら保証しても、130ms 後にしか反応が返ってこなければ精度は体感できない。ボールへの干渉こそがこのゲームの操作そのものなので、そこを遅延させる構成は要件と正面から衝突する。

そこで、サーバーの状態に自分の未確認入力を再適用して**世界全体を現在時刻まで進める**。自分のキックは即座にボールへ反映される。

**他プレイヤーの扱い**: 再シミュレーション中は「サーバーが最後に処理した入力を保持し続ける」と仮定して外挿する。そのためスナップショットには各プレイヤーの最終入力（移動・狙い・キック）を含める。国内 RTT 20〜40ms なら再シミュレーションは **2〜3 ティック**しかないので、外挿の誤差は無視できる。

**訂正の見せ方**: サーバーの状態と予測がズレていた場合、位置を瞬間的に合わせるとカクつく。そこで「訂正前の描画位置」と「訂正後の予測位置」の差を誤差として持ち越し、毎フレーム指数的に減衰させる。3m を超える大きなズレ（得点後のリセットなど）は平滑化せず即座に合わせる。滑りながらワープするほうが不快なため。

## 3. 構成

```
クライアント                          サーバー
─────────────────────────────────────────────────────
入力サンプリング 60Hz
  │ 量子化（1/100 刻み）
  ├─ 世界全体をローカルで1ティック進める（予測）
  │
  └─ 未確認入力をまとめて送信 ──→ 受信・seq で重複排除・キューへ
                                      │
                                60Hz で物理シミュレーション
                                （唯一の正しい世界）
                                      │
  スナップショット受信 ←────── 30Hz でスナップショット配信
  │
  ├─ 確認済みの入力を捨てる
  ├─ 残った未確認入力を再適用して現在時刻へ追いつく
  └─ 生じたズレを誤差として持ち越し、滑らかに減衰させる
```

- **シミュレーション**: 60Hz 固定タイムステップ（`dt = 1/60`）
- **入力送信**: 60Hz。直近の未確認入力を最大10個まとめて送る（パケットロス耐性）
- **スナップショット配信**: 30Hz、固定レイアウトのバイナリ
- **トランスポート**: WebSocket（バイナリフレーム）

WebRTC DataChannel の非信頼モードのほうが理論上は有利だが、シグナリングと NAT 越えの複雑さに対して、国内 RTT 20〜40ms では体感差がほぼ出ない。まず WebSocket で作り、実測して必要なら移行する。

差分圧縮はまだ入れていない。6人フルでもスナップショットは 200 バイト弱、30Hz で約 6KB/s なので、実測して問題になってから足せばよい。

## 4. 入力の量子化 — 予測が壊れる一番の原因

入力の各軸は **-1〜1 を 1/100 刻みに丸めて** 送る（`int8`）。

ここで重要なのは、**クライアントは丸めた値で予測しなければならない**という点。送信時にだけ丸めると、サーバーは丸めた値、クライアントは丸める前の値で計算することになり、**予測が毎ティックわずかにズレ続ける**。`sample()` した直後に `quantizeInput()` を通し、その値をローカル予測にもそのまま使う。

正規化（`normalize`）や長さのクランプ（`clampLength`）は sim 側で行うので、丸めた値を両者が同じように扱えば結果は完全に一致する。

## 5. 時計合わせ

クライアントはサーバーより **片道遅延ぶん先行して**回す必要がある。先行が足りないと入力がサーバーに間に合わず、先行しすぎると自分の操作が相手に届くのが遅くなる。

- 初回スナップショット時に `localTick = serverTick + ceil(rtt/2/dt) + 2` で合わせる
- 以降はサーバーが**未処理入力キューの深さ**をスナップショットに載せて返す
  - `深さ == 0`（サーバーが入力に飢えている）→ 1ティック余分に進めて先行を強める
  - `深さ > 3`（先行しすぎ）→ 1ティック見送る

0 と 3 のあいだに幅を持たせることで、上下に振動せず 1〜3 に落ち着く。

サーバー側は、新しい入力が届いていないティックでは**直前の入力を維持する**。ここで入力を空にすると、パケットが1つ落ちただけで選手が一瞬止まってカクつく。

## 6. 当たり負けと同時接触

ボールへの同時キックは、**サーバーの処理順（ティック順）**で一意に決まる。同一ティック内で複数プレイヤーがキックした場合は、**ボール中心に近いほうを優先**する。

これは物理的な妥当性ではなく、**説明可能性**を優先した規則。「近いほうが勝つ」なら画面を見て納得できる。

## 7. チート対策（現状は最小限）

サーバー権威なので、位置・速度・得点の直接改ざんは原理的に不可能。
残るリスクは「入力の自動化（bot）」だが、友達内で遊ぶ規模ではコストに見合わないため、以下のみ実装する。

- 入力値の**範囲チェック**（`int8` で送るので構造的に -1.28〜1.27 に収まり、sim 側で長さ1にクランプされる）
- 重複・巻き戻し `seq` の破棄

## 8. 計測

体感の議論を主観でやらないために、クライアントに常時デバッグ表示を出している。

| 表示 | 意味 |
|---|---|
| `rtt` | 往復遅延（ms） |
| `tick (+n)` | ローカルティックと、未確認入力の数 |
| `queue` | サーバー側の未処理入力キューの深さ。1〜3 が正常 |
| `fix` | 直近のリコンシリエーションによる最大補正量。**常時大きいなら予測が壊れている** |

`fix` が 0.0cm のままなら、クライアントの予測がサーバーと完全一致している。
