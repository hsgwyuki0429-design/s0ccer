# ネットコード設計

操作精度が最優先の要件なので、ネットワーク層は「入力遅延を体感させない」ことに全振りする。

## 1. 方式の選択

**サーバー権威 + クライアント予測 + リコンシリエーション**を採用する。

### なぜサーバー権威か

チート対策よりも先に、**全員の画面で同じことが起きることを保証するため**。
P2P やクライアント権威だと、ボールの位置が各クライアントでズレて「入った／入ってない」が食い違う。サッカーで得点の判定が食い違うのは致命的。

### なぜロールバック（GGPO 方式）ではないか

格闘ゲームで使われるロールバックは、2人・入力が離散的・巻き戻し量が小さい、という条件で強い。

本作は 6人・入力が連続値・ボールという共有オブジェクトがある。この条件だと他プレイヤーの入力予測を外した際の巻き戻しが頻繁かつ大きく、**ボールが飛ぶ方向が事後的に変わる**という最悪の見え方をする。よって不採用。

## 2. 構成

```
クライアント                          サーバー
─────────────────────────────────────────────────────
入力サンプリング 60Hz
  │
  ├─ 自分の選手をローカルで即座に動かす（予測）
  │
  └─ 入力を連番つきで送信 ──────→ 受信・入力バッファへ
                                      │
                                60Hz で物理シミュレーション
                                （唯一の正しい世界）
                                      │
  スナップショット受信 ←──────── 30Hz でスナップショット配信
  │
  ├─ 自分: 未確認入力を再適用して補正（リコンシリエーション）
  └─ 他人とボール: 100ms 遅延させて補間表示
```

- **シミュレーション**: 60Hz 固定タイムステップ（`dt = 1/60`）
- **入力送信**: 60Hz、直近の未確認入力をまとめて送る（パケットロス耐性）
- **スナップショット配信**: 30Hz、差分圧縮したバイナリ
- **トランスポート**: WebSocket（バイナリフレーム）

WebRTC DataChannel の非信頼モードのほうが理論上は有利だが、シグナリングと NAT 越えの複雑さに対して、国内 RTT 20〜40ms では体感差がほぼ出ない。まず WebSocket で作り、実測して必要なら移行する。

## 3. クライアント予測とリコンシリエーション

自分の選手だけ、入力した瞬間にローカルで動かす。これで**入力遅延の体感がゼロ**になる。

1. 入力に連番 `seq` を振り、送信すると同時にローカルの未確認入力リストへ積む
2. ローカルシミュレーションを1ステップ進める
3. サーバーから「`seq = N` まで処理した」というスナップショットが届く
4. `seq <= N` の入力をリストから捨てる
5. **サーバーが返した自分の状態を正**として、残っている未確認入力を順に再適用する
6. 再適用の結果が現在のローカル状態と一致すれば何も起きない。ズレていれば静かに補正される

**同じ物理コードをサーバーとクライアントで共有する**ことが前提になる。そのため物理シミュレーションは `packages/shared` に置き、サーバー・クライアント双方が同一の実装を読み込む。ここが分岐すると常時ガタつく。

## 4. 他プレイヤーとボールの表示

自分以外は予測せず、**100ms 遅延させたうえで2つのスナップショット間を補間**して表示する。

- 予測しない理由: 他人の入力は分からないため、予測を外すと**位置がワープする**。ワープは遅延よりも遥かに不快
- 100ms の根拠: スナップショット間隔 33ms に対し、1〜2パケットのロスを吸収できる余裕を持たせた値

**ボールも他プレイヤーと同じ扱い**（遅延＋補間）。ボールを予測すると、キックの瞬間に飛ぶ方向が事後修正されて見えるため。

### 結果として起きること

自分の操作は完全に即応するが、他人とボールは 100ms 過去を見ていることになる。
つまり**「相手のボールを奪う」判定には、常にごく短い先読みが要る**。これは方式上避けられないので、隠さずゲーム性の一部として設計に織り込む（コントロール半径 1.2m を広めに取ってあるのはこのため）。

## 5. 当たり負けと同時接触

ボールへの同時キックは、**サーバーの処理順（入力の到着順ではなく、`seq` に紐づくティック順）**で一意に決まる。同一ティック内で複数プレイヤーがキックした場合は、**ボール中心に近いほうを優先**する。

これは物理的な妥当性ではなく、**説明可能性**を優先した規則。「近いほうが勝つ」なら画面を見て納得できる。

## 6. チート対策（Phase 2 では最小限）

サーバー権威なので、位置・速度・得点の直接改ざんは原理的に不可能。
残るリスクは「入力の自動化（bot）」と「タイムスタンプ詐称」だが、友達内で遊ぶ規模ではコストに見合わないため、以下のみ実装する。

- 入力値の**範囲チェック**（移動ベクトルを長さ1に正規化、チャージ時間の上限クランプ）
- 入力レートの上限（60Hz を大きく超える送信を破棄）

## 7. 計測

体感の議論を主観でやらないために、クライアントに常時デバッグ表示を出す。

- RTT
- サーバーティックとローカルティックの差
- リコンシリエーションによる位置補正量（これが常時大きいなら予測が壊れている）
- パケットロス率
